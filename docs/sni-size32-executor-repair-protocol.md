# SNI size32 executor repair protocol v1 (2026-10-13)

**Agent-decided, owner may revisit. Frozen before repair; offline only. No selected task blob fetch.** This amends the implementation details of [executor v1](sni-size32-executor-protocol.md), not the frozen upstream commit, exact 32-row selection (`6ea37fc2bff821ed5cbd5f10352c98b451442f29ee5dbf6bc2029c340c069388`), previous 64 consumed attempts, 1,000,000-byte blob cap, 32,000,000-byte aggregate observed-body cap, 30,000 ms total per request, zero-model/$0 allowance, or strict no-retry rule. An unresolved cleanup or write cannot be converted into a success by a timeout or a later attempt.

1. Before the first request, check the exact private preflight bytes and directory shape. Atomically create a mode-0700 `.size32-custody` directory exclusively; no second runner may acquire it. Retain it even after completion or failure: it is evidence, not a renewable lease. Check its directory identity and emptiness, the expected entries, and the absence of symlinks before each attempt and final report. Failure to acquire or retain custody stops without another request. A compliant runner does not remove a lock or resume an attempted row. Other processes with write access can still tamper: this is fail-stop custody, not a distributed lock or filesystem adversary proof.
2. Use one monotonic 30-second wall deadline starting immediately before fetch, covering fetch, body reads and cancellation. Abort the transport on expiration; bound each awaited fetch/read/cancel with the same remaining deadline. A synthetically injected uncooperative promise cannot block the loop forever. Expiration during an outstanding operation, cancellation rejection or cancellation still pending at deadline is **cleanup-uncertain**: write only its safe terminal failure (with all chunks observed by the application), then stop the entire run, with no report or next request. Do not persist upstream exceptions, response text, raw chunks or arbitrary URL strings. A cooperative timeout with confirmed cleanup may continue; a no-body or HTTP failure with confirmed cleanup may continue. Never launch a second cancellation after an uncertain one.
3. Continue counting every whole chunk yielded by a read, including a chunk that crosses either cap; no content-length/header count may substitute. If the aggregate is reached or exceeded before a later row, stop without writing its attempt or requesting it. If it reaches the cap on the final row, record that row and report only if all 32 have terminal files and cleanup is confirmed. Enforce the same budget after failures and timeouts.
4. The report is assembled **only after all 32 terminal records** from on-disk, bounded-size, exactly shaped JSON records matching each attempt's task/OID. It derives extracted/failed counts and observed-byte sum from those terminal files, then cross-checks the running budget and rechecks output custody. Any missing/duplicate/changed/invalid file is unresolved, not an in-memory-counter report; an exclusive report write error is unresolved.
5. Offline tests must inject hangs in fetch, body read and cancellation (both rejection and pending), check no next request after uncertainty, and test exhaustion before a remaining row. Probe Bun's actual Response/fetch abort behavior against a local synthetic server or stream only, never selected SNI blobs. Rerun focused tests, typecheck, tracked and untracked whitespace checks, private preflight digest/directory readback; obtain a **new independent exact-byte review** before a separately decided live request. An isolated exact-tree `bun run check` and PR-head `Required` remain separate delivery gates. Rights, family independence, novelty, useful cost savings and holdout remain unresolved.
